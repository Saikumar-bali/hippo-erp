# Architecture

Hippo ERP is a frontend-only React + Vite application that uses Supabase as the entire backend.
It follows a Frappe-style ERP product direction (modular business workflows and role-based operations) implemented on Supabase.
Frappe is design inspiration only for ERP conventions; this project does not run a Frappe backend, framework runtime, or Frappe-hosted services.

- Frontend: React + TypeScript + Vite
- Auth: Supabase Auth
- Data: Supabase Postgres
- Authorization: Row Level Security (company scoped)
- Business logic: PostgreSQL RPC functions in `wh` schema

## Runtime Boundaries

- Frontend only uses `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`.
- Service role keys are never used in browser code.
- Stock-changing actions run through RPC, not direct mutable stock writes.

## ERP Foundation Conventions

The application now keeps a shared ERP module registry in `src/lib/erp-modules.ts`. Each entry defines:

- Module key.
- Module label.
- Route convention.
- Icon.
- Required permission.
- Ownership scope: company.
- Status: active or pending.

Document lifecycle and document action conventions are shared in `src/lib/document-status.ts`:

- Lifecycle statuses: `draft`, `pending_approval`, `approved`, `posted`, `cancelled`, `rejected`, `in_transit`, `completed`.
- Actions: `create`, `edit`, `submit`, `approve`, `post`, `cancel`, `reject`, `delete`, `export`.
- Standard transactional fields: `id`, `company_id`, `document_number`, `status`, `workflow_state`, `created_by`, `created_at`, `updated_at`, `posted_at`, `cancelled_at`.

Naming series is planned as company-scoped business numbering, preferably generated by Postgres RPC for transaction safety:

- `GRN-YYYY-00001`
- `ST-YYYY-00001`
- `ADJ-YYYY-00001`
- `CC-YYYY-00001`
- `RES-YYYY-00001`

Standard ERP screens are documented as:

- List view
- Create form
- Edit/detail form
- Report view
- Audit/history section

These conventions are the foundation for the later Product, GRN, Warehouse, Inventory, and Reporting phases.

## Scope Ownership

- ERP module ownership starts after authenticated user and current company context are available.
- Platform-owned (out of ERP scope): company onboarding, membership mapping bootstrap, invite acceptance, and global platform setup.
- Internal compatibility naming remains as `tenant_id` in code/schema until reviewed for migration impact. In this ERP module, that field represents company context.

## Approval Permission Mapping

Future approval workflows are mapped to existing permission keys:

| Permission | Future Flow Usage |
|---|---|
| `qc_grn` | GRN quality control step before posting |
| `approve_grn` | GRN approval before posting to inventory |
| `post_grn` | Final GRN posting that creates stock and movements |
| `approve_adjustment` | Stock adjustment approval before posting |
| `transfer_stock` | Stock transfer creation and completion |
| `approve_cycle_count` | Cycle count variance approval (defined for future use) |

These permissions are already seeded for `owner`, `admin`, and `warehouse_manager` roles.
The `complete_cycle_count` RPC currently enforces role-based access directly; a future workflow can require `approve_cycle_count` for variance approval before automatic posting.

## Core Data Domains

- `app`: company context primitives (currently named tenant tables), profiles, memberships
- `wh`: warehouses, products, stock, movements, GRN, transfers, adjustments, cycle counts, reservations, valuation

## Data API And Future Module Plumbing

Some future inventory screens currently hit `wh` tables directly from the frontend. If the project Data API does not expose `wh`, those screens will throw `Invalid schema: wh` at runtime.

The professional fix for the future module phase is one of:

- Expose the needed `wh` tables to the Data API and keep RLS strict.
- Prefer RPC-backed read endpoints for company-scoped inventory screens.
- Use toast notifications and friendly empty/access states instead of raw schema errors.

This phase documents the foundation only. Product, warehouse, GRN, and valuation screens remain future work.
